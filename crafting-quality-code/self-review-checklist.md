# Self-Review Checklist

代码编写完成后的自检清单。根据代码角色只检查对应维度，详见 SKILL.md 中的 Quality-Pragmatism Balance。

## How to Use

1. 确定代码角色（核心逻辑 / 公开 API / 内部工具 / 胶水代码）
2. 按 SKILL.md 中的平衡表选择要检查的维度
3. 逐项检查，发现问题立即修正
4. 对修正部分重新检查

## 1. Correctness（正确性）

- [ ] 正常输入路径是否产生正确输出？
- [ ] 空值 / null / undefined / 空集合是否处理？
- [ ] 边界条件是否覆盖？（极值、重复、超大输入）
- [ ] 返回值语义是否清晰无歧义？
- [ ] 如果有副作用，是否幂等或副作用被隔离？

**自检方法：** 脑中跑一遍输入路径 — 正常值、空值、边界值、异常值，每个路径的输出是否符合预期。

## 2. Readability（可读性）

- [ ] 6 个月后的我能看懂这段代码吗？
- [ ] 函数/变量命名是否准确描述了它们做什么？
- [ ] 函数是否一屏能看完？（超过 40 行要警惕）
- [ ] 嵌套是否超过 2 层？（是的话用 guard clause）
- [ ] 关键步骤是否有步骤注释？（不加数字编号）
- [ ] 难懂/不直观的地方是否解释了为什么这样做？
- [ ] 有没有晦涩的"聪明"写法需要简化？

**自检方法：** 从调用方的角度读这段代码 — 不看实现，只看函数签名和名字，能理解它做什么吗？

## 3. Robustness（健壮性）

- [ ] 是否信任了不应该信任的输入？（API 响应、用户输入、文件内容）
- [ ] 异常是否被正确处理（不是被吞掉）？
- [ ] 错误信息是否包含足够上下文让调用方理解问题？
- [ ] 资源（连接、文件句柄、锁）是否总是被释放？
- [ ] 有没有可能导致空指针/空值崩溃的地方？

**自检方法：** 假设每个外部依赖都可能失败 — 网络、文件、数据库、第三方 API，每个失败点是否有处理？

## 4. Low Coupling（低耦合）

- [ ] 这个函数/类只有一个改变的理由吗？
- [ ] 依赖是否通过参数/构造函数注入？（不是内部 new 的）
- [ ] 修改这个函数的实现，调用方需要改动吗？
- [ ] 有没有隐式依赖全局状态？
- [ ] 模块间的数据流是否清晰？

**自检方法：** 假设要替换一个依赖（如把 MySQL 换成 PostgreSQL，把 fetch 换成 axios），需要改几个文件？

## 5. Appropriate Extensibility（适度扩展）

- [ ] 核心流程是否面向接口/抽象，没有写死具体实现？
- [ ] 新增同类功能是否需要修改核心逻辑？
- [ ] 有没有 if-else 状态爆炸需要用策略模式/查找表替代？

**反向检查（防止过度设计）：**
- [ ] 是否有只有 1 个实现的抽象层？（可能是过度设计）
- [ ] 是否有"以防万一"的配置项？（可能是过度设计）
- [ ] 是否有比实际需求复杂得多的继承体系？（可能是过度设计）

**自检方法：** 如果现在只需要 A 功能，但设计了 A+B+C 的抽象 — 删掉 B 和 C，等它们真正出现时再加。

## 6. Modern Java Patterns（Java 17+ 现代模式）

- [ ] 不可变 DTO 是否用了 `record`？（而非 Lombok `@Value`）
- [ ] 有限继承体系是否用了 `sealed class`？（而非开放接口）
- [ ] 类型判断是否用了 switch 模式匹配？（而非 if-else instanceof 链）
- [ ] I/O 密集场景是否用了虚拟线程 + `Semaphore`？（而非固定大小线程池）
- [ ] 是否避免了在虚拟线程中使用 `synchronized`？（应改用 `ReentrantLock`）

**自检方法：** 检查代码中是否还在用 Java 8 风格编写 DTO、类型判断和并发代码。如果是 Java 17+ 项目，应充分利用现代特性。

## 7. LLM Integration（LLM 集成）

- [ ] LLM 调用是否有超时控制？
- [ ] LLM 输出解析失败是否有降级处理（默认值）？
- [ ] API Key 是否通过环境变量/配置注入？（不硬编码）
- [ ] 提示词是否集中管理？（不在业务方法中拼接大段字符串）
- [ ] LLM 不可用时核心功能是否仍可运行？

**自检方法：** 假设 LLM 服务完全不可用（超时/宕机/额度用完），系统是否还能提供基本功能？

## 8. Microservices（微服务）

- [ ] 服务间调用是否配置了超时和重试？
- [ ] 外部服务调用是否有熔断/降级策略？
- [ ] 敏感配置（数据库密码、API Key）是否从配置中心读取？
- [ ] API 路径是否包含版本号（如 `/api/v1/`）？
- [ ] 缓存是否有过期策略和穿透防护？

**自检方法：** 假设某个依赖服务突然变慢（10s 响应），当前服务会不会被拖垮？

## 9. Strategy + Factory（策略工厂）

- [ ] 策略接口是否有明确的类型 ID 方法？
- [ ] 工厂是否用 `@PostConstruct` + Map 注册（不是 if-else）？
- [ ] 策略未找到时是否抛明确异常（不返回 null）？
- [ ] 新增策略是否只需加 `@Service` 类，无需改工厂？

**自检方法：** 检查代码中是否有按类型 ID 做 if-else 分发的逻辑。如果有，用策略工厂替代。

## 10. SSE Streaming（SSE 流式推送）

- [ ] `SseEmitter` 是否设置了合理的超时和回调（onCompletion/onTimeout/onError）？
- [ ] 是否有心跳保活防止连接被代理关闭？
- [ ] 发送事件时是否处理了 `IOException`？
- [ ] 客户端断连后资源（线程、连接映射）是否被清理？

**自检方法：** 假设客户端在 SSE 连接建立后立即断网，服务端会不会泄漏线程或内存？

## 11. Distributed Lock（分布式锁）

- [ ] 锁的 key 是否精确到业务 ID（如 `lock:order:123`）？
- [ ] `leaseTime` 是否大于业务最长执行时间？
- [ ] 锁释放是否在 `finally` 块中，且检查 `isHeldByCurrentThread`？
- [ ] 是否避免了锁嵌套（容易死锁）？

**自检方法：** 假设获取锁后业务执行到一半进程被 kill，锁会不会自动释放？会不会误释放别人的锁？

## 12. Vector Search / RAG（向量检索）

- [ ] embedding 模型和查询模型是否一致（维度、版本）？
- [ ] 检索 topK 和相似度阈值是否合理？
- [ ] 向量数据库索引是否已创建（不是查询时才报错）？
- [ ] 是否有 embedding 缓存避免重复计算？

**自检方法：** 用一段已知内容检索，返回的结果是否语义相关？如果不相关，检查 embedding 模型和索引配置。

## Fix Loop

发现问题后的修正流程：

```
发现问题 → 定位根因 → 修正 → 对修正部分重新跑检查清单 → 直到全部通过
```

**常见修正模式：**

| 问题类型 | 典型修正 |
|---------|---------|
| 命名不清 | 重命名变量/函数，让名字表达意图 |
| 函数太长 | 提取子函数，每个子函数单一职责 |
| 边界未处理 | 在函数入口加 guard clause |
| 异常被吞 | 删除空 catch，改为处理或传播 |
| 依赖硬编码 | 提取为参数/构造函数注入 |
| 过度设计 | 删除未使用的抽象层，退化为简单实现 |
| 设计不足 | 从 if-else 提取策略接口 |
| LLM 无降级 | 加 try-catch + 默认返回值 |
| 虚拟线程用 synchronized | 改用 `ReentrantLock` |
| 微服务无超时 | 配置 Feign/HTTP client 超时 + 重试 |
| if-else 类型路由 | 提取策略接口 + 工厂注册 |
| SSE 无心跳/无清理 | 加心跳定时 + onCompletion 回调清理 |
| 分布式锁无超时 | 设置 leaseTime > 业务最长执行时间 |
| 耗时操作在事务内 | 用 TransactionSynchronization.afterCommit 延迟执行 |

**Final check:** 这段代码我敢直接提交到 master 吗？如果犹豫，说明还有问题。

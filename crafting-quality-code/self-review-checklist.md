# Self-Review Checklist

代码编写完成后的自检清单。根据代码角色只检查对应维度，详见 SKILL.md 中的 Quality-Pragmatism Balance。

## How to Use

1. 确定代码角色（核心逻辑 / 公开 API / 内部工具 / 胶水代码）
2. 按 SKILL.md 中的平衡表选择要检查的维度
3. 逐项检查，发现问题立即修正
4. 对修正部分重新检查

## 1. Correctness（正确性）

- [ ] 正常输入路径是否产生正确输出？
- [ ] 空值 / null / undefined / 空集合是否处理？
- [ ] 边界条件是否覆盖？（极值、重复、超大输入）
- [ ] 返回值语义是否清晰无歧义？
- [ ] 如果有副作用，是否幂等或副作用被隔离？

**自检方法：** 脑中跑一遍输入路径 — 正常值、空值、边界值、异常值，每个路径的输出是否符合预期。

## 2. Readability（可读性）

- [ ] 6 个月后的我能看懂这段代码吗？
- [ ] 函数/变量命名是否准确描述了它们做什么？
- [ ] 函数是否一屏能看完？（超过 40 行要警惕）
- [ ] 嵌套是否超过 2 层？（是的话用 guard clause）
- [ ] 注释是否只解释 why，没有复述 what？
- [ ] 有没有晦涩的"聪明"写法需要简化？

**自检方法：** 从调用方的角度读这段代码 — 不看实现，只看函数签名和名字，能理解它做什么吗？

## 3. Robustness（健壮性）

- [ ] 是否信任了不应该信任的输入？（API 响应、用户输入、文件内容）
- [ ] 异常是否被正确处理（不是被吞掉）？
- [ ] 错误信息是否包含足够上下文让调用方理解问题？
- [ ] 资源（连接、文件句柄、锁）是否总是被释放？
- [ ] 有没有可能导致空指针/空值崩溃的地方？

**自检方法：** 假设每个外部依赖都可能失败 — 网络、文件、数据库、第三方 API，每个失败点是否有处理？

## 4. Low Coupling（低耦合）

- [ ] 这个函数/类只有一个改变的理由吗？
- [ ] 依赖是否通过参数/构造函数注入？（不是内部 new 的）
- [ ] 修改这个函数的实现，调用方需要改动吗？
- [ ] 有没有隐式依赖全局状态？
- [ ] 模块间的数据流是否清晰？

**自检方法：** 假设要替换一个依赖（如把 MySQL 换成 PostgreSQL，把 fetch 换成 axios），需要改几个文件？

## 5. Appropriate Extensibility（适度扩展）

- [ ] 核心流程是否面向接口/抽象，没有写死具体实现？
- [ ] 新增同类功能是否需要修改核心逻辑？
- [ ] 有没有 if-else 状态爆炸需要用策略模式/查找表替代？

**反向检查（防止过度设计）：**
- [ ] 是否有只有 1 个实现的抽象层？（可能是过度设计）
- [ ] 是否有"以防万一"的配置项？（可能是过度设计）
- [ ] 是否有比实际需求复杂得多的继承体系？（可能是过度设计）

**自检方法：** 如果现在只需要 A 功能，但设计了 A+B+C 的抽象 — 删掉 B 和 C，等它们真正出现时再加。

## Fix Loop

发现问题后的修正流程：

```
发现问题 → 定位根因 → 修正 → 对修正部分重新跑检查清单 → 直到全部通过
```

**常见修正模式：**

| 问题类型 | 典型修正 |
|---------|---------|
| 命名不清 | 重命名变量/函数，让名字表达意图 |
| 函数太长 | 提取子函数，每个子函数单一职责 |
| 边界未处理 | 在函数入口加 guard clause |
| 异常被吞 | 删除空 catch，改为处理或传播 |
| 依赖硬编码 | 提取为参数/构造函数注入 |
| 过度设计 | 删除未使用的抽象层，退化为简单实现 |
| 设计不足 | 从 if-else 提取策略接口 |

**Final check:** 这段代码我敢直接提交到 master 吗？如果犹豫，说明还有问题。

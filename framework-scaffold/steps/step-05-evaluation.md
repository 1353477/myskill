## 评价序列

### 1. 六维度评价

从以下维度评价架构：

**1. 业务匹配度**
- 评分：高/中/低
- 说明：架构对确认的业务需求服务得如何？
- 证据：将关键模块追溯到具体需求

**2. 可扩展性**
- 评分：高/中/低
- 说明：架构能否随业务增长？
- 证据：新增模块/功能的难易程度

**3. 性能**
- 评分：高/中/低
- 说明：架构能否满足确认的性能需求？
- 证据：如何处理预期负载

**4. 可维护性**
- 评分：高/中/低
- 说明：代码库维护和修改的难易程度？
- 证据：关注点分离、代码组织、依赖管理

**5. 开发效率**
- 评分：高/中/低
- 说明：团队使用这个架构的产出效率？
- 证据：框架约定、工具链、社区支持、团队熟悉度

**6. 技术风险** — 注意：低风险 = 好
- 评分：低/中/高（低 = 低风险 = 好）
- 说明：主要技术风险是什么？
- 证据：新技术/未验证技术、复杂集成、单点故障

### 2. 识别已知局限性

明确陈述本架构不擅长处理的场景：

- "本架构假设单区域部署，多区域需要..."
- "实时功能未涉及，WebSocket 集成需要..."
- "当前设计未包含消息队列，如果需要异步处理..."

### 6. 处理用户调整

如果用户要求调整：

1. 讨论调整及其影响
2. 如需更新步骤 4 的架构设计则更新
3. 重新评价受影响的维度
4. 重新展示更新后的评价
5. 用户选择 [C] 前禁止继续

### 7. 阶段门禁过渡

用户选择 [C] 时：

1. 用最终评价更新 `{design-docs}/03-architecture-design.md`
2. 更新 frontmatter：
   ```yaml
   stepsCompleted: [1, 2, 3, 4, 5]
   status: design_confirmed
   confirmedAt: '{{current_date}}'
   ```
3. 明确说：
   "架构方案已确认，接下来我将开始搭建项目。我会创建完整的项目结构、生成代码骨架、配置文件、数据库迁移脚本和 Docker 环境。"
4. 加载 `./step-06-project-init.md`
